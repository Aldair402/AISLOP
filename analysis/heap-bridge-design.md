# Puente entre backend principal y Rayon: invariantes y primer experimento

## Qué se ha probado

La prueba Rust `tests::rayon_shared_identity_and_concurrent_initialization` en `mc-aot/src/main.rs` combina **solo prototipos** existentes: `SharedHeap`, `ClassInit` y el scheduler Rayon. En 20 rondas, cuatro tareas Rayon y el hilo llamador compiten por inicializar una clase; se comprueba una inicialización, publicación de un mismo objeto desde un campo estático, autoalias, monitor reentrante y 500 incrementos protegidos por ronda (10.000 en total), rechazo de un `ObjectId` de otro heap y cierre sin panics. Pasó `cargo test` (59 unitarias + 25 de integración; `analysis/roadmap-cargo-test.log`) y la suite integral de 286 etapas (`analysis/full-regressions-roadmap.log`). No ejecuta bytecode Java, no usa el heap de `multi-static-demo`, no prueba excepciones Java ni demuestra el modelo de memoria JVM.

## Primer puente experimental en el heap del backend principal

`numeric_runtime.inc` tiene ahora un mecanismo **interno y opt-in**, todavía no expuesto al bytecode Java, para convertir un `Array::Obj` ordinario en `SharedObj`: mueve el vector de campos existente a `Arc<Mutex<Vec<V>>>`, sin copiar los campos ni cambiar el índice de la referencia Java. El backend numérico sigue leyendo/escribiendo esos mismos campos; su despacho de objetos, comprobaciones de tipo y lectura de clase reconocen también la nueva representación. Las operaciones sueltan el mutex antes de retornar y no ejecutan callbacks bajo él. El handle solo ofrece lectura, escritura e incremento acotado de campos `int`; no revela referencias crudas. La identidad se basa en el `Arc`, y resolver un handle requiere comprobar que pertenece al heap correspondiente: dos heaps distintos pueden tener el mismo índice. Objetos especiales, incluidos `LocalObj`, se rechazan. El handle puede sobrevivir al heap, pero no puede acceder a referencias del heap ya destruido. No hay recolección ni política de reclamación adicional.

`mc-aot/tests/check-numeric-object-sharing.py` compila bytecode de un fixture Java mediante **el backend principal**, y activa el puente solo en el código Rust generado por la prueba. 64 resultados Java coinciden con el ejecutable sin y con el puente (incluye alias, despacho de interfaz, `instanceof`, `getClass` y extremos de int). Un harness Rust sobre ese mismo runtime y métodos generados ejecuta 20 rondas, 4 tareas Rayon y 4.000 incrementos atómicos experimentales por ronda, intercalados con 1.000 actualizaciones de otro campo mediante bytecode Java traducido, y comprueba alias, identidad, pertenencia, tipos, desbordamiento y mutex envenenado. Un oráculo Java independiente usa incrementos `synchronized` y `ForkJoinPool` y coincide en el resultado final del caso concreto. Adicionalmente, 64 consultas secuenciales usan `FeatureFlagUniverse` del JAR oficial (SHA-256 de clase `61e490913ad43b3f0137a8fd3f310856ef8b06c32051cbc80bc3bfb7c211e2c0`): el objeto se comparte mediante la misma inyección de prueba y su método `toString` sin modificar lee su campo String a través del backend principal. No se envía ese campo ni esa clase a las tareas Rayon. Detalles en `analysis/numeric-object-sharing-validation.log`. La suite completa posterior pasó 290 etapas (`analysis/full-regressions-numeric-object-sharing.log`).

## Referencias entre objetos compartidos — segundo experimento

`shared_object_reference` acepta el heap numérico propietario, un handle y un campo. Verifica primero que el handle pertenece a ese heap, toma el campo bajo el mutex, suelta el mutex y solo después resuelve el índice privado y convierte el objeto ordinario destino a la misma representación compartida. Retorna un handle del destino o `None`, sin exponer índices; sigue alias y ciclos sin mantener dos locks. Un cambio posterior del campo no invalida un handle ya entregado y una lectura posterior observa la nueva referencia. Campos no referencia, índices inexistentes, handles de otros heaps, mutex dañado y destinos no modelados (incluidos arrays, String y `LocalObj`) se rechazan. El helper requiere `&mut Heap`: **solo el propietario puede navegar**, y las tareas reciben handles ya resueltos; no ofrece navegación autónoma en workers ni escritura de referencias.

`mc-aot/tests/check-numeric-shared-references.py` compara 96 decisiones de bytecode Java traducido, activando el puente por inyección solo en el Rust de la prueba. Comprueba autoalias indirecto, ciclo entre dos objetos, `null`, reasignación por bytecode y que dos heaps con mismo índice no se confunden. En 20 rondas, 4 tareas Rust/Rayon actualizan ambos objetos (8.000 incrementos por ronda en total), mientras el bytecode principal actualiza otro campo y cambia una referencia; el resultado final se compara con un oráculo Java `synchronized` para el escenario concreto. Además, 96 resultados sobre **tres clases oficiales sin modificar** (`FeatureFlag`, `FeatureFlagSet` y `FeatureFlagUniverse`, hashes verificados en el test) contrastan referencias compartidas al mismo universo. Este caso real es secuencial. Resultados en `analysis/numeric-shared-references-validation.log`.

## Monitor reentrante para objetos compartidos — tercer experimento

El objeto numérico compartido tiene un monitor propio en el handle (identidad compartida al clonarlo), con propietario por hilo, contador reentrante y `Condvar`. El backend principal usa ese mismo monitor al ejecutar `monitorenter`, `monitorexit` y `Thread.holdsLock` sobre un `SharedObj`; los objetos no compartidos siguen con su ruta monohilo. Se rechaza la conversión de un objeto ordinario si su monitor monohilo ya está adquirido. El candado de campos no se retiene al esperar por el monitor. En salida incorrecta se conserva `IllegalMonitorStateException`; el envenenamiento o desbordamiento del monitor se rechazan como fallos internos. La guarda Rust de worker no es `Send`.

`mc-aot/tests/check-numeric-shared-monitors.py` compara 96 decisiones de un fixture Java con y sin puente, incluyendo método `synchronized`, bloque reentrante, `holdsLock` y excepciones. En un harness que usa el **runtime y métodos numéricos generados**, 4 tareas Rust/Rayon y el bytecode del hilo principal compiten por el mismo monitor: 20 rondas de 5.000 incrementos no atómicos protegidos, con resultado contrastado frente a un oráculo Java. Prueba además salida desde hilo no propietario, liberación durante desenrollado, reentrada, monitor previo adquirido, envenenamiento, límite de profundidad, guarda no `Send` y rechazo en compilación de `Object.wait`. La activación es inyectada en el Rust de prueba, no se activa desde el bytecode. Ver `analysis/numeric-shared-monitors-validation.log`. La suite integral posterior terminó con 292 etapas y exit 0 (`analysis/full-regressions-numeric-shared-monitors.log`).

## Bytecode Java de tarea sobre el mismo objeto — perfil AOT acotado

El nuevo modo `shared-worker-demo` verifica y traduce un patrón estricto `Runnable.run → método synchronized → incremento de un int` a una función Rust ejecutada en cuatro tareas Rayon. El hilo principal ejecuta métodos Java traducidos por el backend numérico sobre el mismo objeto y monitor, y espera todas las tareas antes de leer el resultado. El objeto `Runnable` no se materializa: solo se comprueba su constructor de captura canónico y se elimina en este scheduling controlado. No se compilan las instrucciones Java de construcción, envío o espera de `ForkJoinPool`. Opcionalmente se verifica por hash y bytecode y traduce el reenvío de `TickTask.run` o `Util$4.run` oficiales hacia la tarea acotada, sin materializar esos wrappers ni admitir subclases, `getTick`, colas, nombres o `toString`. La programación y capturas siguen controladas por Rust; TickTask no implica que el servidor lo envíe a ForkJoinPool.

Las clases, flags, descriptores, instrucciones y referencias se validan, rechazando formas distintas; se contempla también `QuartPos.toBlock(1)` cuando su bytecode puro e inicialización se verifican. Hay 32 ejecuciones diferenciales sintéticas y 31 con `QuartPos` oficial sin modificar; 18 guardas de clases/bytecode/captura, rechazo de QuartPos modificado y entradas inválidas (`analysis/shared-worker-bytecode-validation.log`). Solo se afirma equivalencia para este patrón y configuración. No implementa tareas Java arbitrarias, `ForkJoinPool`, `Future`, callbacks, interrupciones o excepciones de tarea Java. Ver el comando y las restricciones en `mc-aot/README.md`.

## Camino paralelo: capturas en el backend concurrente

El backend concurrente aislado (`SharedHeap`, no el heap numérico) admite opt-in capturas finales de referencias a objetos de proyecto finales sin jerarquía/interfaces/`<clinit>`, con comprobación del tipo exacto y escritura limitada al constructor. Esto permite ejecutar bytecode Java que construye un `ForkJoinPool`, crea cuatro tareas que comparten un objeto y su monitor, hace `submit`/`join`/`shutdown` y modifica el objeto simultáneamente desde el hilo llamador. Una segunda variante materializa `TickTask` oficial con hash fijado, traduce `run`/`getTick` y despacha el `Runnable` capturado; usa también `QuartPos` oficial. Hay 28 comparaciones Java/Rayon por variante, y guardas (`analysis/rayon-java-captured-object-validation.log`, `analysis/rayon-real-ticktask-capture-validation.log`). No implementa excepciones Java generales, subclases de TickTask, interrupción o colas, ni está integrado en `Main` o en el heap numérico. La suite integral posterior pasó 297 etapas (`analysis/full-regressions-rayon-captures.log`).

## Puente de objeto real entre SharedHeap y heap numérico

`SharedHeap` puede registrar explícitamente un adaptador interno `ExternalObject` para acceder a campos `int` o referencias validadas y adquirir el monitor suministrados por el objeto numérico original. No duplica el vector ni el monitor. La tabla de identidad está asociada al `SharedHeap`, la inscripción repetida de la misma identidad devuelve el mismo `ObjectId`, y los IDs de un heap ajeno se rechazan. El lock global de `SharedHeap` se libera antes de llamar al adaptador o esperar por el monitor; CAS/RMW externo se rechazan. El contrato de identidad del adaptador es interno, no una interfaz segura para adaptadores arbitrarios.

En `tests/check-numeric-concurrent-bridge.py` el harness concatena explícitamente el Rust de ambos traductores e incluye `numeric_concurrent_bridge.inc`. Verifica el classfile de un `Cell` final y su único campo `I`; no deduce el tipo Java solo de `V::I`. El código numérico ejecuta llamadas traducidas sobre `Cell`; el concurrente traduce el bytecode Java de creación del pool, capturas, `submit`, `join` y `shutdown`, con cuatro tareas. Comparación contra Java 25 en 20 rondas, `QuartPos` oficial, desbordamiento, mismo objeto y monitor, reentrada cruzada, bloqueo, desbloqueo al desenrollar, guardas de tipos/heap y binario sin Java en PATH (`analysis/numeric-concurrent-bridge-validation.log`).

Este primer adaptador **no integra automáticamente el compilador**, ni comparte estáticos, referencias de campos, otros tipos, inicialización de clases o excepciones Java. La publicación, verificación del layout, unión de los outputs y scheduling de la entrada se realizan en el harness; la llamada Java que uniría ambos heaps no se traduce. El monitor no implementa wait/notify. No está conectado a Main, y el fixture no representa una clase completa validada. La integral posterior terminó con exit 0 y 300 etapas, incluyendo ambos puentes y la variante TickTask (`analysis/full-regressions-numeric-concurrent-graph-ticktask.log`).

## Referencias finales entre objetos, con sesión explícita

Un segundo adaptador `numeric_concurrent_graph_bridge.inc` registra cada objeto numérico en un mapa por sesión: índice local del heap propietario ↔ `ObjectId` de `SharedHeap`, con clase exacta y layout de campos. La identidad del heap propietario se conserva con un token `Arc` exclusivo; se rechaza registrar objetos de otro heap o sesión incompatible. Las referencias finales se pueden **leer**, no escribir, y solo resuelven objetos ya registrados del tipo exacto; nulos se conservan. Se rechazan destinos no registrados, layout/etiqueta incompatibles, IDs ajenos, cierre de sesión y operaciones CAS/RMW externas. `SharedHeap` también comprueba que una referencia devuelta por un adaptador pertenece al mismo heap, y no retiene su mutex mientras se consulta el adaptador. No hay subtipos ni referencias a arrays o String.

`check-numeric-concurrent-graph.py` verifica el classfile sintético de `Node` (final, directo de Object, campo `int` y campo `final Node`) y une los outputs generados de ambos backends. Cuatro tareas Java con `ForkJoinPool` navegan la referencia traducida hacia un objeto numérico y lo incrementan con el mismo monitor utilizado por el llamador; 20 rondas por variante frente a Java 25 con `QuartPos` oficial, overflow, alias y guardas. La segunda materializa también el `TickTask` oficial y ejecuta `run` y `getTick` antes de la captura; no implica que el servidor lo envíe al pool (`analysis/numeric-concurrent-graph-validation.log`, `analysis/numeric-concurrent-graph-ticktask-validation.log`). La verificación del layout, unión de outputs, registro y publicación son explícitos en el harness y no se generan desde el programa Java. No se comparten estáticos ni clases, no se traducen excepciones Java generales y no hay integración de Main. La integral posterior al primer puente se interrumpió para incorporar esta ampliación; no es evidencia de éxito completo.

**Límites críticos:** la operación `add_int` es una primitiva atómica interna de la prueba, no la traducción de `i++`, `volatile` ni `synchronized`; no modela la semántica Java de carreras. Las tareas Rayon de los primeros harness son closures Rust; el modo posterior solo traduce el patrón Java indicado arriba. El puente no enlaza `SharedHeap`/frames concurrentes con el backend numérico, no comparte estáticos, strings, arrays, clases ni excepciones, y no implementa inicialización multihilo, callbacks, esperas o ciclo de vida. Los monitores de objetos no compartidos y de clases siguen siendo monohilo; el monitor compartido cubre solo la entrada/salida/holdsLock probados. `Object.wait`/`notify`, interrupciones y tareas Java generales en workers no están implementados. El modo opt-in usa el puente explícitamente, pero no habilita `ForkJoinPool` en Main. Esto es una primera pieza de representación compartida y una prueba integrada controlada, no un puente completo ni validación de servidor.

## Incompatibilidades reales

- El backend principal usa `numeric_runtime.inc`: `Heap` posee `Vec<Array>`, estáticos `Vec<V>` y tablas internas; operaciones generadas reciben `&mut Heap`. Sus referencias son índices `usize` ligados a ese heap y su inicialización es monohilo (`init_states`).
- El prototipo `SharedHeap` usa `ObjectId` (identidad de heap más índice), `Arc<Mutex<Store>>` y valores `Int`, `Long`, `Ref` y `Void`. Los frames son privados de cada hilo; `ClassInit` es una barrera separada. No modela todas las variantes de `Array`, excepciones, clases ni el ciclo de vida del runtime principal.
- Una copia entre heaps destruiría alias, mutaciones compartidas, identidad, monitores y caches de `Class`/String. Pasar o convertir índices entre heaps sin mapeo verificado es incorrecto. Mantener `&mut Heap` simultáneamente desde threads sería inseguro; bloquear el heap entero durante callbacks/esperas puede provocar deadlocks.

El plan y las guardas del experimento de monitor se conservaron en `analysis/next-numeric-shared-monitor.md`.

## Siguiente diseño comprobable

1. Extender el experimento de handles de objetos a una representación compartida única o un puente completo; verificar pertenencia, ownership, vida útil y orden de monitores. El experimento actual comparte campos `int` y un monitor de objetos ordinarios y resuelve sus referencias solo desde el heap propietario, pero no el resto del heap.
2. Llevar de uno en uno al heap compartido los tipos que el camino real usa (instancias, arrays, cadenas, clases, excepciones y estáticos), con pruebas de identidad, alias y límites. Evitar bloqueo global retenido al ejecutar bytecode o entrar a un monitor.
3. Unificar inicialización de clase con estados compartidos, dependencia, reentrada y fallos Java traducidos; verificar publicación y contención, no solo el conteo de inicializadores.
4. Ampliar el patrón opt-in de tarea Java AOT para admitir bytecode, objetos, errores y programación de tareas reales; integrar envío y espera expresados por el programa Java, no solo el scheduling externo del demo. Comparar Java y nativo bajo contención sin asumir orden no especificado.
5. Solo después conectar la factory/worker reales de `Util.makeExecutor`, incluyendo logger real o adaptador verificado, handler y shutdown; no silenciar los efectos. Los estados de Tracy/JFR deben ser explícitos y contrastados.

La prueba actual facilita detectar regresiones en los componentes pero no es ese puente. El error actual de Main sigue siendo `ForkJoinPool`; la suite y el roadmap completo están en `ROADMAP.md`.
