# Siguiente bloqueo: pipeline de StackLocator en Log4j 2.26.0

El probe `real-eula-objects-tostring-attempt.log` no compila todavía. Su primer bloqueo es `Stream.dropWhile(Predicate)` al bajar `StackLocator.lambda$getCallerClass$2`. Es un diagnóstico de compilación, no ejecución ni prueba de Eula, logger, concurrencia o servidor.

En el bytecode multi-release Java 25 del StackLocator oficial, la ruta `getCallerClass(Class,Predicate)` valida ambos argumentos y hace `WALKER.walk`: su lambda construye `frames.map(StackFrame::getDeclaringClass).dropWhile(c -> !sentinel.equals(c)).dropWhile(c -> sentinel.equals(c) || !callerPredicate.test(c)).findFirst().orElse(null)`. La búsqueda puede necesitar frames fuera del prefijo traducido, que se rechazan; no devolver null como si se hubiera alcanzado el final real.

Para implementarlo de verdad hacen falta etapas perezosas map/dropWhile sobre StackWalkStream y findFirst con ejecución secuencial, estados de consumo, short-circuit, propagación de excepciones, retención de clase y cierre del scope. La segunda etapa conserva su estado tras el primer fallo del predicado; no es equivalente a filter. Los callbacks anidados deben incluir frames JDK opacos para que otra inspección de pila aborte al cruzarlos. Cualquier operación no modelada debe seguir fallando explícitamente. El soporte actual de Stream.map solo construye la etapa sobre fuentes de colección modeladas; no consume dicha etapa y no admite el stream de StackWalker.

Validar frente a Java 25 con casos de sentinel inicial/intermedio/ausente, predicados con cambios de estado y excepción, null, pila anidada y callbacks que inspeccionan la pila; probar el bytecode oficial exacto con las mismas cadenas de frames conocidas y guardas para externos. Después repetir el probe sin anticipar cuál será el siguiente bloqueo, y no incorporar stubs de logger al runtime principal. También siguen pendientes Set.stream().sorted().map().filter().findFirst() y el comparador de PropertySource, con orden, laziness y efectos correctos, antes de validar el logger real. Además no hay integración del scheduler Rayon en el backend Main.
