# Próximo paso: monitor de objetos del heap numérico compartido

Este documento fue el plan para el experimento implementado después en `numeric_runtime.inc`; el detalle y resultados están en `analysis/heap-bridge-design.md` y `analysis/numeric-shared-monitors-validation.log`. El experimento usa un monitor reentrante para `SharedObj`, pero el resto de los monitores conserva `Heap.monitors` monohilo. El backend principal **no ejecuta tareas Java en Rayon**. `concurrent_heap.rs` contiene otro monitor para su heap experimental, no el heap numérico.

## Propuesta y condiciones

1. Asociar a cada `NumericObjectHandle` un monitor reentrante con `Mutex`/`Condvar`, propietario `ThreadId` y profundidad. Clonar handles debe conservar un único monitor y campo. Una guarda Rust de worker no puede ser `Send`, porque la salida corresponde al hilo propietario. Ningún método que espere el monitor puede mantener el mutex de campos.
2. Al compartir un objeto numérico previamente monohilo, **rechazar explícitamente si ya tiene un monitor adquirido**; convertirlo en ese estado sin trasladar el propietario y profundidad provocaría dos monitores. El backend numérico debe consultar `SharedObj` al entrar, salir y en `Thread.holdsLock`, no seguir usando `Heap.monitors` para ese objeto. Los demás objetos conservarán la ruta actual mientras no se compartan.
3. La salida de un monitor no adquirido o de otro hilo debe seguir produciendo `IllegalMonitorStateException` donde el backend lo modela; envenenamiento, profundidad no representable u otras condiciones internas deben abortar/rechazarse explícitamente, sin fingir una excepción Java. Revisar desenrollado de las rutas `synchronized` y `monitorenter`/`monitorexit`, incluidos handlers Java.
4. Contrastar un fixture Java con `synchronized`, reentrada y `Thread.holdsLock`, y un harness sobre el Rust generado donde tareas Rayon y bytecode principal compiten por el **mismo monitor y objeto**. Incrementos no atómicos deben protegerse con ese monitor; el resultado debe compararse con Java sin suponer orden de llegada. Probar excepción/salida y transferencia rechazada mientras está adquirido. Añadir timeouts y pruebas negativas de propietario distinto.
5. Mantener bajo guarda `wait`, `notify`, interrupciones, monitores de clases y tipos especiales hasta modelarlos; no confundir el mecanismo de `Condvar` interno para la entrada con `Object.wait`/`notify`. Aun si pasa la prueba, closures Rust ejecutándose en Rayon no son métodos Java ejecutándose en Rayon, y el heap y la inicialización global seguirán siendo monohilo.

La integral sobre referencias terminó con 291 etapas antes de aplicar el experimento de monitor; la integral posterior terminó con 292 etapas y exit 0 (`analysis/full-regressions-numeric-shared-monitors.log`).
