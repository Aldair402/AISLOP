# Siguiente integración: executor Java y heap numérico

## Estado verificado

- El backend numérico puede compartir un objeto ordinario mediante `NumericObjectHandle`, incluyendo su monitor, pero los workers del modo `shared-worker-demo` solo ejecutan un patrón de tarea especializado y el pool lo programa el harness Rust.
- El backend concurrente usa `SharedHeap`, frames por tarea y `Executors` sobre Rayon. Con `MC_AOT_RAYON_PROJECT_REFERENCES=1`, un `Runnable` final puede capturar una referencia final a un objeto de proyecto final restringido. El fixture ejecuta las instrucciones Java de `new ForkJoinPool`, `submit`, `join` y `shutdown` y comparte el objeto entre cuatro tareas y el llamador. También se comprobó una ruta que materializa `TickTask` oficial y despacha su `Runnable.run` (`rayon-java-captured-object-validation.log`, `rayon-real-ticktask-capture-validation.log`).
- Dos adaptadores de prueba enlazan objetos entre ambos heaps sin copiar campos ni monitor. El segundo permite leer una referencia final a otro objeto ya registrado por la misma sesión; las tareas Java traducidas la navegan (`numeric-concurrent-graph-validation.log`). La unión, los layouts y la publicación son manuales en el harness, y no se comparten estáticos ni clases.
- Los dos heaps no son el mismo. La prueba de `TickTask` no ejecuta `MinecraftServer`, no implementa su cola de ticks y no demuestra que el servidor envíe `TickTask` a `ForkJoinPool`. `MinecraftServer.wrapRunnable` y `shouldRun` son llamadores directos, pero no se han compilado ni ejecutado (`ticktask-callers-current.log`).

## Obstáculos que hay que resolver antes de conectar Main

1. **Identidad y titularidad:** asignar un identificador estable por objeto y heap. Un handle ajeno debe fallar; dos referencias Java al mismo objeto deben terminar en la misma identidad nativa. No copiar el vector de campos en dos heaps independientes.
2. **Campos y tipos:** decidir una única representación compartida de valores y referencias, con comprobación de pertenencia y tipos. Determinar cómo se tratan arrays, String, referencias cíclicas, publicación, límites y vida del objeto. El puente actual cubre int y lectura de referencias finales registradas, sin copiar campos; no cubre el heap de Minecraft.
3. **Monitor único:** las operaciones del backend numérico y del concurrente deben bloquear el mismo monitor reentrante, sin sostener el mutex global de campos mientras se espera. `monitorenter`, `monitorexit`, métodos `synchronized`, liberación al desenrollar y propiedad por hilo tienen que coincidir. `wait`/`notify` e interrupciones siguen sin implementación y deben rechazarse.
4. **Clases y estáticos:** acordar una tabla única de identidad y estados de inicialización, publicar valores una vez, gestionar reentrada, hilos que esperan y fallos de inicialización. La preparación anticipada del perfil concurrente no equivale a la inicialización perezosa JVM.
5. **Invocaciones y frames:** la llamada principal y los callbacks de tareas deben ejecutar código traducido sobre la misma representación. Evitar mantener un `&mut Heap` o mutex global durante `join` o una llamada que pueda adquirir un monitor o ejecutar callbacks: produciría bloqueo o aliasing inválido. Establecer explícitamente orden de locks y puntos de suspensión.
6. **Executor:** llevar constructores, `execute`/`submit`, `join`, espera y cierre pertinentes al backend principal. Rechazar explícitamente cancelación, interrupción, `shutdownNow`, Tracy activo, factories/handlers o excepciones generales no modelados. El perfil Rayon no garantiza orden global de tareas ni el ciclo de vida completo de Java.
7. **Fallos:** distinguir excepciones Java de errores internos del traductor/runtime. No convertir un panic Rust o un límite de pasos en una excepción Java supuestamente equivalente. Probar propagación de errores de tareas antes de aceptar rutas que dependen de ella.

## Primera puerta de integración

Ya existe un fixture que expresa en bytecode Java la creación de un pool y cuatro tareas, pero solo el backend concurrente traduce esa creación: el harness de prueba une ambos outputs y publica el objeto. El siguiente fixture debe expresar en bytecode Java también la publicación y enviarse al backend principal, sin ensamblaje ni programación manuales; después adquirir el monitor desde llamador y workers, hacer `join` y observar el mismo estado. Contrastar contra Java 25; verificar alias, tipos, desbordamiento, clase fallida, reentrada, pertenencia a heaps diferentes, guardas de excepciones y ejecución nativa con PATH sin Java. Las pruebas deben cubrir serialización e intercalado, sin asumir orden no especificado. Añadir después una ruta con `TracingExecutor` oficial, Tracy desactivado mediante guarda explícita, y comprobar cierre; no afirmar que el logger ni el ciclo de vida completo funcionan.

Solo después repetir el probe de `Main`. Si aparece la factory real `Util.makeExecutor`, preservar el comportamiento observado de su lambda, nombres, callbacks y logger, o detenerse en una guarda explícita. No sustituirlos por stubs silenciosos. Una prueba de método no certifica la clase completa.

## Oráculo nuevo: handler real del pool (Java solamente)

`analysis/forkjoin-handler-java25-oracle.log` registra 20 rondas con `ForkJoinPool(1, defaultFactory, handler, true)`: una excepción de `execute(Runnable)` llega al handler como el mismo objeto; una tarea fallida de `submit` queda reflejada en `join` y `get` sin invocar el handler; y una tarea fallida de `CompletableFuture.supplyAsync` queda en el future sin invocar el handler. También comprueba terminación y rechazo tras shutdown. Es un fixture sintético y un oráculo Java, no compara Rust ni implementa el handler de `Util.onThreadException`, logging o `CrashReport`. Las excepciones generales y la traducción de la lambda/handler real siguen pendientes. Este test adicional aún no está integrado en la integral en ejecución.
